# Repo Vibecheck v0.2 Policy and Integrations Design

## Goal

Make Repo Vibecheck practical for gradual CI adoption across applications, libraries, CLIs, and templates. Version 0.2 adds repository policy configuration, applicable-score semantics, baseline/diff gating, richer deterministic claim parsing, SARIF and GitHub summaries, labeled benchmark regression checks, and stronger privacy around opt-in execution.

## Configuration and project profiles

The scanner loads `repo-vibecheck.yml` or `repo-vibecheck.yaml` from the target root unless `--config <path>` is supplied. Configuration is optional and validated strictly. Unknown keys or invalid values produce a usage error.

Supported configuration:

```yaml
projectType: auto # auto | app | library | cli | template
failOn: error
offline: true
redact: true
ignore:
  findings: [env.example-unused]
  paths: [generated/**]
requirements:
  disable: [deployment]
execution:
  passEnv: [DATABASE_URL]
```

CLI flags override configuration. Auto profile uses manifest signals; an explicit `--project-type` override is also supported. The effective profile and configuration path appear in JSON reports.

Profiles control applicability, not detector truth. Libraries do not lose points merely because Docker, deployment, runtime env setup, or executable baselines are inapplicable. Apps retain the complete policy. CLI and template profiles use narrower applicability sets.

## Score semantics

Each category becomes:

```ts
type CategoryScore = {
  status: "scored" | "not_run" | "not_applicable";
  score: number | null;
  maxScore: number;
};
```

The total score is normalized over categories with `status: scored`. `scoreCoverage` reports applicable scored weight divided by total possible applicable weight. Unrequested build/test is `not_run`, not zero. Inapplicable profile categories are `not_applicable`.

JSON schema advances to 2.0 because category score types change.

## Baseline and diff

`--write-baseline <file>` writes a deterministic baseline containing schema version, target-independent finding fingerprints, and requirement statuses. `--baseline <file>` classifies findings as new, unchanged, or resolved.

Fingerprints use stable fields: finding ID, category, normalized message, normalized evidence path, requirement concept, and status. Absolute paths and timestamps are excluded.

When a baseline is supplied, `--fail-on` applies only to new findings and new requirement regressions. Reports include baseline summary and per-finding baseline state.

## Claim extraction

Deterministic claim parsing adds:

- requirement IDs such as `AUTH-01`
- nested bullet acceptance criteria
- indented multiline continuation text
- line/source metadata
- common aliases
- explicit negation detection (`no auth required`, `must not use Docker`)

Negated requirements are represented as constraints and are never converted into positive feature claims. Arbitrary semantic reasoning and LLM calls remain out of scope.

## Report formats

`--format human|json|sarif` replaces format-specific flags while preserving `--json` as a deprecated-compatible alias. `--output <file>` writes the selected report atomically; terminal output remains the default when omitted.

SARIF 2.1.0 maps finding IDs to rules, severity to SARIF levels, and file/line evidence to locations when available. Requirement matches without locations are emitted as logical results.

When `GITHUB_STEP_SUMMARY` is present, the Action writes a concise Markdown summary with score, coverage, new/resolved counts, requirement statuses, and a production-readiness disclaimer. SARIF is generated as an Action output file suitable for upload.

## Benchmark labels

Each pinned corpus entry adds expected project types, allowed finding IDs, and known false-positive IDs. Benchmark output includes project-type agreement, unexpected finding IDs, missing expected IDs, and regression delta against the checked-in baseline.

Five repositories remain a smoke/regression corpus, not a statistically meaningful precision/recall dataset. Documentation states this explicitly.

## Security and privacy

- The Action adds `offline`, `redact`, `config`, and `baseline` inputs.
- Action defaults are `offline: true` and `redact: true`.
- Registry checks occur only when online mode is explicitly selected by the Action user.
- `--run-*` child processes receive a sanitized environment containing only a small runtime allowlist plus `execution.passEnv`/CLI allowlist entries.
- Timeout termination kills process trees on Windows and process groups on POSIX.
- Redaction masks common token/secret assignment patterns, authorization values, user-home prefixes, and values of secret-like env names in evidence and command errors.
- GitHub first-party actions are pinned to immutable commit SHAs and annotated with release names. Dependabot configuration tracks updates.

## Compatibility

- Node.js 20+ and ESM remain unchanged.
- Existing scans without config continue to work.
- `--json` remains accepted.
- Existing finding IDs remain stable where possible.
- Schema 2.0 is an intentional JSON contract break documented in the changelog.
